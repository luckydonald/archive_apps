## GarageBand (error 15): stale checksumfile from pre-fix checksums_from_zip

The checksumfile was written during an earlier `--verify-new`/`--verify-zips` run
(when it was missing) by the old `checksums_from_zip` that called
`locale.setlocale(LC_ALL, '')` before sorting — switching to en_US.UTF-8.
After commit 44c7bd1 pinned `checksums_from_zip` to `LC_COLLATE=C`, the sort
order of `_CodeSignature/` and other `_`-prefixed paths changed, so the stored
checksumfile no longer matches what the fixed function produces.

Fix: delete `GarageBand.app@10.4.12.checksums.txt` and re-run verify; the
missing-checksumfile branch will recreate it with the correct sort order.

## Xcode (error 14): _find_zip64_offset guard too strict for ZIP64 entries in first 4 GB

Xcode's 4.7 GB zip is a ZIP64 archive. Python's `zipfile` has a bug: when
individual file sizes are < 4 GB but a file's *position* needs a 64-bit offset,
Python misassigns the offset to `info.file_size` and leaves
`info.header_offset = 0xFFFFFFFF`. `z.open(info)` seeks to the wrong place and
throws for every affected entry.

The `_find_zip64_offset` workaround scanned the ZIP64 extra field but required
`v > 0xFFFFFFFF` — only true for entries positioned *after* the 4 GB mark.
~85% of Xcode's 118,024 entries live in the first 4 GB (offsets ≤ 0xFFFFFFFF),
so the guard silently returned None for all of them.

The `_hash_via_unzip` last-resort fallback also failed because macOS ships
Info-ZIP 6.00 (2009), which has incomplete ZIP64 support and cannot correctly
seek to entries whose central-directory offset needs 64-bit addressing.

Result: 114,968 entries unreadable → user renamed zip to .bak.zip.

Fix applied (this session): removed the `v > 0xFFFFFFFF` guard in
`_find_zip64_offset`; the function now tries every 8-byte field in the ZIP64
block and validates with the `PK\x03\x04` local-header signature. The signature
check prevents false positives from file-size fields. Entries in the first 4 GB
are now recoverable via `_hash_at_offset`, making the broken `unzip` fallback
largely moot for ZIP64 archives.
